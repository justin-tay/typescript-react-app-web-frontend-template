# HTTP security headers

The HTTP response header posture of the web frontend is recorded here against the [OWASP HTTP Security Response Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html). It is a planning and verification aid, not a conformance claim.

## What the frontend sends, and what it does not

The frontend is static files. Its build output, `dist/`, carries no response headers: whatever serves those files decides every header in production. The only place the frontend's own code sets headers is its **development server**, through the plugin in `vite-plugin-csp.ts`, so a policy mistake shows up while developing. That plugin sets exactly three things, all on the page: a nonce-based `Content-Security-Policy`, a report-only Trusted Types policy, and `Cache-Control: no-store`.

The "Current value" column records what was observed on 2026-10-01 from the Vite 8.3.1 development server and from `vite preview`, which serves the production build. `vite preview` sends no security headers at all, not even the policy, so it is not a model of production and must not be used to serve the application.

| Source                             | Response headers observed for the page                                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Development server (`npm run dev`) | `Content-Security-Policy` (enforced), `Content-Security-Policy-Report-Only: require-trusted-types-for 'script'`, `Cache-Control: no-store`, `Content-Type: text/html`, `Vary: Origin` |
| `vite preview` (production build)  | `Content-Type: text/html`, `Cache-Control: no-cache`, `Etag`, `Vary: Origin`; no policy                                                                                               |
| Production                         | Whatever the host sends. See the rows below and the [required production decisions](#required-production-decisions).                                                                  |

The backend's JSON responses carry their own header set (`default-src 'none'`, `nosniff`, `no-store`, a referrer policy and a permissions policy, per its HTTP security headers document in `java-app-web-api-server-template`). That set describes the API, not this page.

## Required production decisions

Before the built files are served to real people, the owner of the deployment must decide and record the following, then fetch a served page and check the headers actually received:

1. **The content security policy for the page.** The built `index.html` has the nonce placeholder `__CSP_NONCE__` on three tags. The host must replace it with a fresh random value on every response and send a `Content-Security-Policy` with the same nonce, no `'unsafe-inline'`, no `ws:` or `wss:`, and `frame-ancestors 'none'`. Decide where violations are reported.
2. **No caching of `index.html`.** Send `Cache-Control: no-store` on it, since a cached copy would carry an old nonce. Decide the directives for hashed assets.
3. **The remaining page headers**, which the development server does not send: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy` (keeping WebAuthn working), `Content-Type: text/html; charset=UTF-8`, and optionally `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and `X-Robots-Tag`.
4. **Parity in development.** Add the same headers to `vite-plugin-csp.ts` so a header that breaks the application fails in development, as the policy already does.
5. **The edge.** Check what the CDN or proxy adds or strips (`Server`, `X-Powered-By`, HSTS preload).

A sample server configuration, and a check that fetches a served page and asserts these headers, would turn this list into something that can be tested (see risk 1 in [section 11](../../11-risks-and-technical-debt.md)).
